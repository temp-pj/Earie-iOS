# iOS 랜덤 매칭 요구사항

> **이 문서의 목표:** 무엇을 왜 만드는지를, 어떤 에이전트가 읽어도 같은 결과물이 나오게 정한다.
>
> **이 문서에 두지 않는 것:** 기술 선택과 내부 구조는 design.md, 작업 나누기는 tasks.md에 둔다. 서버와 주고받는 메시지 형식은 새로 쓰지 않고, 같은 폴더의 `protocol.md`(서버 v1 복사본)를 따른다.

- 상태: 확정
- 버전: v1.0
- 작성일: 2026-11-25
- 바깥 계약: 같은 폴더의 `protocol.md`와 `fixtures/`. 서버 저장소에서 복사한 읽기 전용 사본이며, 출처와 기준 SHA는 `SOURCE.md`에 있다.
- 배경 참고 (읽지 않아도 작업할 수 있다): [서버 requirements.md v1.1](https://github.com/temp-pj/Earie-ws/blob/8a7587fc17d61875a3f7312ae16904df7e721e78/docs/specs/random-matchmaking/requirements.md). iOS가 지켜야 할 동작은 이 문서에 모두 옮겨 두었다.

---

## 1. 목적

- 해결하려는 문제: 지금 iOS 앱은 방 ID를 입력해 바로 방에 들어가는 구 서버 방식이다. 서버는 v1 랜덤 매칭으로 바뀌었고 구 방식 연결을 거절하므로, 앱으로는 게임을 시작할 수 없다.
- 사용자가 얻어야 하는 경험: 로비에서 음악 조건을 고르고 매칭 버튼을 누르면, 조건이 맞는 다른 사람과 같은 방에 들어가 게임을 하고, 끝나면 로비로 돌아와 다시 매칭할 수 있다.
- 성공했다고 볼 모습: 시뮬레이터 두 대가 로컬 v1 서버에 붙어 매칭, 방 입장, 시작, 퇴장, 재매칭까지 사람 개입 없이 자동 테스트로 통과한다. 취소 직후 도착한 응답이나 이전 방의 메시지 때문에 화면이 엉뚱하게 바뀌는 일이 없다.

## 2. 주요 사용자 흐름

앱 실행 → 로비(조건 선택) → 매칭 버튼 → 매칭 대기 → 방 입장 → 방장이 시작 → 게임 10라운드 → 결과 → 나가기 → 로비(이전 조건 유지) → 다시 매칭

## 3. 범위와 비범위

### 이번에 하는 것
- SCOPE-01: v1 엔드포인트(`/ws?protocolVersion=1`) 연결과, protocol.md v1의 모든 메시지 인코딩·디코딩
- SCOPE-02: `fixtures/catalog-projection.json`(`test-v1`)을 앱에 번들하고 읽기
- SCOPE-03: 로비의 조건 선택(연대, 구성, 성별, 장르)과 선택 불가능한 조합 비활성화, 마지막 선택 저장·복원
- SCOPE-04: 매칭 요청, 매칭 대기, 취소
- SCOPE-05: 매칭 실패와 연결 실패 처리
- SCOPE-06: 방 화면(참가자, 방장, 시작, 나가기)과 강퇴 수신 처리
- SCOPE-07: 기존 게임 흐름을 v1 메시지(roomID 포함)에 연결하고, 게임 조기 종료(GAME_ABORTED) 처리
- SCOPE-08: 결과 화면과 로비 복귀, 같은 연결로 재매칭
- SCOPE-09: v1과 겹치는 구 코드 삭제 (구 Category, 구 START_GAME 경로, RoomSessionClient, 미사용 RoomClient, 디버그 ContentView, 이번 변경으로 고아가 된 도메인 타입)
- SCOPE-10: CI에 테스트 실행 추가, `fixtures/` 기반 코덱 테스트, 로컬 서버에 실제로 붙는 iOS 통합 테스트

### 이번에 하지 않는 것
- OUT-01: 로그인 (Login Feature와 AuthClient는 건드리지 않는다. 앱은 로비에서 시작한다)
- OUT-02: 디자인과 MDS 적용 (기본 SwiftUI 컴포넌트만 쓴다)
- OUT-03: 실제 곡 카탈로그와 그 생성 도구 (서버 T10). 이번에는 `test-v1`만 쓴다
- OUT-04: 실제 음원 재생 검증 (`test-v1`의 ISRC는 재생되지 않는다)
- OUT-05: 재접속 복구, 백그라운드 연결 유지
- OUT-06: 강퇴를 보내는 UI(KICK_PLAYER 송신), 방 ID 입장, 직접 방 만들기, 친구 초대, 같은 방 재시작, 제한 시간 선택
- OUT-07: 서버 코드와 protocol.md 변경

## 4. 다음 작업이 기대하는 것

| 다음 작업 | 그 작업이 기대하는 동작 | 이번 작업이 보장할 것 |
|---|---|---|
| 실제 카탈로그 적용 (서버 T10 이후) | 카탈로그 파일만 바꾸면 실제 곡으로 동작 | 카탈로그 내용(버전, 연대, 장르 목록, 조합)을 코드에 하드코딩하지 않고 번들 파일에서만 읽는다 |
| 디자인 적용 | 화면 모양만 바꾸면 됨 | 화면에 필요한 모든 정보와 버튼 활성 여부가 Reducer 상태로 표현되고, View는 상태를 그리기만 한다 |
| 서버 계약 버전 변경 | 복사본(`protocol.md`, `fixtures/`) 교체로 어긋남을 발견 | 코덱 테스트가 `fixtures/` 전체를 통과해야 한다 |

## 5. 용어 정의

| 용어 | 정의 | 아닌 것 |
|---|---|---|
| 조건 / 조합 | 연대, 구성, 성별, 장르 네 축의 값 묶음 (protocol.md의 Category) | 축 하나의 값 |
| 상관없음 | wire 값 `any`. 상대 조건을 받아들인다 | `all` |
| 모든 연대 | 연대 축의 wire 값 `all`. 카탈로그의 전체 연대 범위 | 상관없음 |
| 카탈로그 | 앱 번들에 들어 있는 projection 파일(`catalog-projection.json` 형식). 곡 목록 없이 버전, 연대, 장르, 허용 조합, 풀별 곡 수만 담는다 | 서버의 catalog.json이나 manifest |
| 허용 조합 | 카탈로그 `allowedRequests`에 들어 있는 조합 | 축마다 따로 유효한 값 |
| 연결 | WebSocket 연결 하나. 새 연결은 서버에서 새 사용자다 | 방 |
| 활성 요청 | 매칭 대기 중인, 취소되지 않은 매칭 요청 하나와 그 requestID | 취소한 요청 |
| 현재 방 | 마지막으로 받은 유효한 WELCOME의 방. ROOM_LEFT, 강퇴, 연결 끊김으로 없어진다 | 이전에 있던 방 |
| 로비 | 조건 선택과 매칭 대기를 포함하는 화면 단계 | 방 대기 화면 |

## 6. 우선순위

1. 정확성: 늦은 응답, 이전 방 메시지, 순서 때문에 잘못된 화면이나 상태가 되지 않는다
2. 계약 준수: protocol.md v1과 다른 형식을 보내지 않는다
3. 단순함
4. 화면 완성도

- 충돌 예시와 그때의 선택: 취소 버튼을 누른 뒤 서버의 MATCH_CANCELLED를 기다렸다가 로비로 가면 더 "확실"해 보이지만, 서버 요구사항이 "취소 즉시 로비"이고 늦은 응답은 requestID로 거를 수 있으므로 즉시 이동한다.

## 7. 규칙

### 카탈로그와 조건 선택
- REQ-CAT-01: 로비는 연대, 구성, 성별, 장르 네 축을 각각 하나씩 고르게 한다. 모든 축의 기본값은 상관없음이다.
- REQ-CAT-02: 연대 축에만 "모든 연대" 선택지를 제공한다. 나머지 축에는 전체를 뜻하는 선택지를 두지 않는다.
- REQ-CAT-03: 연대와 장르의 선택지 목록과 표시 순서는 카탈로그의 `decades`, `genres` 배열을 따른다. 장르 이름은 `label`을 표시한다.
- REQ-CAT-04: 축 X의 후보 값 v는, 허용 조합 중 "X의 값이 v이고, 나머지 각 축은 현재 값이 상관없음이면 아무 값이든, 아니면 현재 값과 같은" 조합이 하나라도 있으면 활성, 없으면 비활성이다. 후보가 상관없음이면 항상 활성이다. 비활성 후보는 비활성으로 표시하고, 사용자가 고른 다른 축의 값을 자동으로 바꾸지 않는다.
  - 근거: 상관없음은 "아무 값이나 받아들인다"는 뜻이므로, 그 축은 후보 판정에서 제약이 되지 않는다. protocol.md 문구("바꾼 결과가 완전한 허용 조합이어야 한다")를 글자 그대로 적용하면, 허용 조합에 `2010s / any / any / any`가 없는 test-v1에서 `2010s / any / any / korean_ballad`에 도달할 수 없다.
  - 버린 대안: 바꾼 결과가 허용 조합에 있을 때만 활성 (위 이유). 후보 값을 포함한 허용 조합이 하나라도 있으면 활성 (다른 축의 현재 선택과 함께 쓸 수 없는 후보까지 켜진다).
- REQ-CAT-05: 현재 조합이 허용 조합에 없으면 매칭 버튼을 비활성화한다.
- REQ-CAT-06: 카탈로그를 읽지 못했거나, `allowedRequests`가 비었거나, 전부 상관없음 조합이 허용 조합에 없으면 매칭 버튼을 비활성화하고 "지금은 매칭을 이용할 수 없어요"를 표시한다.
  - 근거: protocol.md "전부 any조차 유효하지 않으면 매칭 비활성 및 이용 불가 표시"
- REQ-CAT-07: 매칭 버튼을 눌러 매칭을 시작할 때 그 조합을 기기에 저장한다. 매칭이 실패하거나 취소되어도 저장한 값은 그대로 둔다. 로비에 들어올 때마다(앱 재실행 포함) 저장한 조합을 복원한다.
  - 근거: 매칭을 시작했다는 것이 사용자가 그 조합을 원했다는 근거이고, 실패나 취소로 그 의도가 바뀌지 않는다.
- REQ-CAT-08: 복원한 조합이 현재 카탈로그의 허용 조합에 없으면 전부 상관없음으로 시작한다.
  - 근거: 앱 업데이트로 카탈로그가 바뀌면 예전 조합이 불가능해질 수 있다.

### 매칭
- REQ-MATCH-01: 매칭 버튼을 누르면 즉시 매칭 대기 화면으로 바뀐다. 네트워크 결과를 기다리지 않는다.
- REQ-MATCH-02: 살아 있는 연결이 있으면 재사용하고, 없으면 새로 연결한다. 연결만으로 방에 들어가지 않는다.
- REQ-MATCH-03: MATCH_REQUEST에는 새 requestID(소문자 UUID v4), 번들 카탈로그의 `version`, 현재 조합을 담는다.
- REQ-MATCH-04: 활성 요청은 최대 하나다. 매칭 대기 중에는 새 매칭 요청을 보내지 않는다.
- REQ-MATCH-05: 매칭 대기는 시간 제한 없이 유지한다. 조건을 자동으로 완화하지 않는다.
- REQ-MATCH-06: 활성 요청의 MATCH_WAITING은 화면을 바꾸지 않는다.
- REQ-MATCH-07: 활성 요청의 WELCOME을 받으면 방 화면으로 바뀌고, WELCOME의 방 정보(roomID, 내 playerID, 방장, 참가자 순서, 최대 인원, 확정 조합)로 방을 표시한다.

### 취소
- REQ-CANCEL-01: 매칭 대기 화면의 취소 버튼을 누르면 즉시 조건 선택 화면으로 돌아가고 MATCH_CANCEL을 보낸다. 알럿은 띄우지 않는다.
- REQ-CANCEL-02: 취소한 requestID로 이후에 오는 MATCH_WAITING, WELCOME, MATCH_FAILED, MATCH_CANCELLED는 화면과 상태를 바꾸지 않는다.
- REQ-CANCEL-03: 취소 직후 바로 다시 매칭할 수 있다. 새 요청은 새 requestID를 쓴다.
- REQ-CANCEL-04: 연결이 아직 맺어지는 중에 취소하면, 연결이 맺어진 뒤에도 그 요청의 MATCH_REQUEST를 보내지 않는다. 맺어진 연결은 닫지 않는다.

### 실패와 연결
- REQ-FAIL-01: 활성 요청의 MATCH_FAILED를 받으면 아래 문구로 알럿을 띄우고 조건 선택 화면으로 돌아간다.
  - INVALID_CRITERIA: "음악 조건 정보가 변경됐어요. 앱 업데이트를 확인해 주세요."
  - INTERNAL_ERROR: "매칭 중 문제가 생겼어요. 잠시 후 다시 시도해 주세요."
  - ALREADY_MATCHING: "이미 매칭 중이에요."
  - ALREADY_IN_ROOM: "이미 방에 참여 중이에요."
  - 근거 (INVALID_CRITERIA): 앱은 허용 조합만 보내므로, INVALID_CRITERIA는 사실상 카탈로그 버전 불일치를 뜻한다.
- REQ-FAIL-02: 매칭 대기, 방, 게임, 결과 중에 연결이 끊기거나 연결 시도가 실패하면 "서버와 연결이 끊어졌어요." 알럿을 띄우고 조건 선택 화면으로 돌아간다. 방 상태는 버리고 복구하지 않는다. 다음 매칭 때 새 연결을 맺는다. 활성 요청도 현재 방도 없는 조건 선택 화면에서 연결이 끊기면 알럿 없이 연결 상태만 바꾼다.
- REQ-FAIL-05: 연결 시도 후 10초 안에 연결되지 않으면 연결 실패로 처리한다.
  - 근거: 서버의 pong 대기와 쓰기 제한(10초)과 맞춘다.
- REQ-FAIL-03: 앱은 취소, 퇴장, 강퇴를 이유로 연결을 닫지 않는다.
- REQ-FAIL-04: 해석할 수 없는 메시지(형식 오류, 모르는 type)는 버린다. 앱이 종료되지 않는다.

### 방
- REQ-ROOM-01: 방 화면은 참가자 목록(서버가 준 순서), 방장 표시, 내 표시, 현재 인원과 최대 인원, 확정 조합을 보여준다.
- REQ-ROOM-02: PLAYER_JOINED, PLAYER_LEFT, HOST_CHANGED를 받으면 목록과 방장을 갱신한다.
- REQ-ROOM-03: 시작 버튼은 내가 방장이고, 참가자가 2명 이상이고, 방이 대기 상태이고, 나가는 중이 아닐 때만 활성화한다. START_GAME에는 roomID만 담는다.
- REQ-ROOM-04: ROOM_COMMAND_FAILED를 받으면 방 화면에 머물며 아래 문구로 알럿을 띄운다.
  - NOT_HOST: "방장만 게임을 시작할 수 있어요."
  - NOT_ENOUGH_PLAYERS: "2명 이상일 때 시작할 수 있어요."
  - INVALID_STATE: "지금은 게임을 시작할 수 없어요."
  - INTERNAL_ERROR: "게임을 시작하지 못했어요. 다시 시도해 주세요."
- REQ-ROOM-05: 나가기 버튼을 누르면 LEAVE_ROOM을 보내고 "나가는 중" 상태가 된다. 현재 방의 ROOM_LEFT를 받으면 조건 선택 화면으로 돌아간다. 연결은 유지한다.
  - 근거: 서버 REQ-CONN-04 "ROOM_LEFT 확인으로 로비 복귀". 확인 전에 화면을 바꾸면 서버에는 아직 참가자로 남아 있을 수 있다.
- REQ-ROOM-06: 나가는 중에는 나가기 버튼을 다시 보내지 않고, 시작 버튼을 비활성화한다. 그 사이 도착한 현재 방의 이벤트는 그대로 반영한다.
- REQ-ROOM-07: 현재 방의 PLAYER_KICKED를 받으면 "방에서 내보내졌어요." 알럿을 띄우고 조건 선택 화면으로 돌아간다. 연결은 유지한다.
- REQ-ROOM-08: 게임 화면에 나가기 버튼을 둔다. 누르면 "게임에서 나갈까요?" 확인창을 띄우고, 확인하면 REQ-ROOM-05를 따른다. 방 대기와 결과 화면의 나가기는 확인창 없이 바로 REQ-ROOM-05를 따른다.
  - 근거: 명시적인 퇴장 수단이 없으면 사용자가 앱을 백그라운드로 보내는 방식으로 나가게 된다. 이때 연결이 바로 끊긴다는 보장이 없어서, 서버가 그 사람의 곡 준비 완료를 기다리다 30초 뒤 남은 사람 모두의 게임을 GAME_ABORTED(INTERNAL_ERROR)로 끝낼 수 있다. 확인창은 글자 카드를 누르다 잘못 누르는 것을 막는다.
- REQ-ROOM-09: 시작 버튼을 누르면 START_GAME을 보내고 '시작 요청 중' 상태가 된다. 이 상태에서는 시작 버튼이 비활성이다. 게임 시작 응답 또는 ROOM_COMMAND_FAILED를 받으면 상태가 풀린다.

### 게임과 결과
- REQ-GAME-01: 현재 방의 GAME_STARTED를 받으면 게임 화면으로 바뀐다. 라운드 진행, 글자 카드, 정답 제출, 오답 페널티, 카운트다운, 라운드 결과는 기존 GameReducer 동작을 유지한다.
- REQ-GAME-02: PRELOAD_SONG을 받으면 곡을 준비하고, 준비가 끝나면 같은 roomID와 roundNumber로 READY_TO_PLAY를 보낸다. 준비에 실패하면 READY_TO_PLAY를 보내지 않고 서버의 처리(GAME_ABORTED)를 기다린다.
  - 근거: 서버가 30초 preload 제한으로 게임을 끝내므로, 앱이 따로 판단하면 서버와 결과가 갈린다.
- REQ-GAME-03: SUBMIT_ANSWER와 READY_TO_PLAY에는 현재 roomID를 담는다.
- REQ-GAME-04: 현재 방의 GAME_OVER를 받으면 결과 화면으로 바뀌고, 승자와 점수를 보여준다. 승자가 빈 문자열이면 승자 없음으로 표시한다.
- REQ-GAME-05: 현재 방의 GAME_ABORTED를 받으면 음악을 멈추고 결과 화면으로 바뀐다. 점수와 승자는 표시하지 않는다. 결과 화면에 사유별 문구를 표시한다. INSUFFICIENT_PLAYERS: "상대가 모두 퇴장했습니다" / INTERNAL_ERROR: "문제가 생겨 게임이 중단됐어요."
- REQ-GAME-06: 결과 화면에는 나가기 버튼만 있다. 재시작은 없다. 나가기는 REQ-ROOM-05를 따른다.
- REQ-GAME-07: 로비로 돌아온 뒤 매칭하면, 연결이 살아 있는 한 같은 연결을 재사용한다.

### 메시지 거르기
- REQ-FILTER-01: requestID가 있는 매칭 메시지(MATCH_WAITING, MATCH_CANCELLED, MATCH_FAILED, WELCOME)는 requestID가 활성 요청과 같을 때만 처리한다.
- REQ-FILTER-02: roomID가 있는 방·게임 메시지는 roomID가 현재 방과 같을 때만 처리한다. ROOM_LEFT는 나가는 중인 현재 방과 같을 때만 처리한다.
- REQ-FILTER-03: 거른 메시지는 화면과 상태를 바꾸지 않고 로그만 남긴다.

## 9. 경계와 예외

- EDGE-01: 취소 직후 그 요청의 WELCOME이 도착한다 → 무시한다. 서버가 그 요청의 방 참가를 정리한다.
- EDGE-02: 매칭 버튼을 빠르게 여러 번 누른다 → MATCH_REQUEST는 한 번만 나간다.
- EDGE-03: 취소하고 곧바로 다시 매칭한다 → 새 requestID로 요청한다. 이전 요청의 응답은 무시하고, 새 요청의 응답만 처리한다.
- EDGE-04: 연결이 맺어지는 중에 취소한다 → 연결 후에도 MATCH_REQUEST를 보내지 않는다 (REQ-CANCEL-04).
- EDGE-05: 연결이 맺어지는 중에 취소하고 다시 매칭한다 → 연결이 맺어지면 새 요청 하나만 보낸다.
- EDGE-06: WELCOME 바로 뒤에 같은 방의 PLAYER_JOINED가 온다 → WELCOME으로 방을 만든 뒤 PLAYER_JOINED를 반영한다. 순서가 바뀌지 않는다.
- EDGE-07: 방을 나와 새 방에 들어간 뒤 이전 방의 메시지가 도착한다 → 무시한다.
- EDGE-08: 같은 방의 ROOM_LEFT가 두 번 오거나, 다른 roomID의 ROOM_LEFT가 온다 → 첫 번째 현재 방 ROOM_LEFT만 처리하고 나머지는 무시한다.
- EDGE-09: 방에 나 혼자 남는다 → 시작 버튼이 비활성화된다. 방에 머물 수 있다.
- EDGE-10: 방장이 나가서 내가 방장이 된다 → HOST_CHANGED로 방장 표시와 시작 버튼 활성 판정이 바뀐다.
- EDGE-11: 곡 준비 중에 상대가 모두 나간다 → GAME_ABORTED(INSUFFICIENT_PLAYERS)로 결과 화면, 음악 정지.
- EDGE-12: 곡 준비가 실패한다 (`test-v1`에서는 항상) → READY_TO_PLAY를 보내지 않고, 약 30초 뒤 서버의 GAME_ABORTED(INTERNAL_ERROR)를 받아 결과 화면으로 간다.
- EDGE-13: 나가는 중에 GAME_STARTED가 온다 (시작과 퇴장 경합) → 게임 화면으로 바뀌되 나가는 중 상태를 유지하고, ROOM_LEFT를 받으면 조건 선택으로 간다.
- EDGE-14: 저장해 둔 조합이 카탈로그에 없다 → 전부 상관없음으로 시작한다.
- EDGE-15: playerID나 roomID 자리에 UUID가 아닌 문자열이 온다 → 그 메시지를 버리고 앱은 계속 동작한다.
- EDGE-16: 알 수 없는 필드가 붙은 메시지가 온다 → 그 필드만 무시하고 메시지를 처리한다.
